# Forge Design Studio · 统一预览与视觉评审操作规范

> 角色边界：本文说明 **Studio 如何组织、呈现、检查设计**。肾宝保 User Job、医疗事实、状态/Owner、导航及实现合同仍以 `docs/mvp2/product/v2/**` 和原有 `docs/mvp2/design/design-rules.md` 为准；生产 Token/组件以 SwiftUI `DesignSystem/AppTheme` 为唯一 Owner。本文不创建第二套产品合同、Golden 或 Release Gate。

## 一条设计工作流

1. **Product Truth**：为一个 Screen/Flow Family 明确用户任务、可核验的完成标准、事实及其唯一 Writer。列出创建、编辑、删除、更正、历史、下游影响。
2. **IA / Interaction**：按事实类型选原生控件；展示正常、空、加载、错误、权限/通知降级、成功与恢复状态。先确认页面间真实入口和返回路径。
3. **Visual Direction**：在 Forge Design Studio 的唯一模块/页面导航中预览同一个注册表里的具体状态；按同一用户任务和屏幕条件比较 V1 与 V2，固定主次视觉层级，再做细节。
4. **Review / Convergence**：结合产品语义、真实浏览器原型交互、无障碍与最新截图独立检查；候选预览及其 Markdown 导出**不代表**已接受的 Golden。问题归到对应模块原 Requirement/Plan/Work，不新建并行 Authority。
5. **Implementation**：产品和视觉方案确认后，映射既有 DesignSystem 组件、Token 和路由；Simulator 验证关键旅程，检查最新截图与跨页数据一致性。

## 一页视觉的具体裁决

| 维度 | 通过时应看到什么 | 不接受的捷径 |
|---|---|---|
| 任务层级 | 第一屏能识别当前事实、下一步最重要动作；主要 CTA 通常只有一处 | 多个同权蓝色按钮、功能墙 |
| 阅读顺序 | 标题→核心事实→主要动作→辅助信息；日期、数值、单位对齐；必要摘要最先 | 层叠卡片替代真实信息结构 |
| 视觉系统 | 复用蓝白基调、既有语义 Token、字级与 spacing；轻边线主要用于状态/分界 | 新建第二主题、强渐变、重投影、Card-in-Card |
| 输入与反馈 | 单位、日期、枚举、等级用专门控件；保存/更正/取消、错误和恢复可区分 | 万能文本框、假的保存成功 |
| 医疗语义 | 已发生 Evidence 默认只读，未知/0/无记录不同；没有未经证实的临床评价 | 用绿色/红色暗示未核验的医学好坏 |
| 无障碍 | iOS 可操作区域至少 44×44pt，动态字体、VoiceOver 标签和顺序、键盘/长文案可用 | 靠缩小字体、固定高度裁切、只有颜色的反馈 |
| 一致性 | 同语义共享组件、值/单位/状态颜色一致；不同病种允许有不同首页信息层级 | 为了看起来统一而复制每个页面布局 |

## Studio 工作区约定

- **左侧**：项目 → 产品模块 → 页面与状态，可搜索页面。页面集合来自项目原有静态注册表，Studio 不复制页面 ID。
- **中间**：单页面高保真候选，提供屏幕序号和前后浏览；iframe 隔离运行，仅用于预览，不写入产品数据。
- **右侧**：当前页面身份、视觉检查提醒、模块源码与合同交接。Markdown 导出只包含明确列出的源文件和产品约束，便于 Gemini 重新组织 UI；模型建议需回到原设计合同审查，不能直接覆盖 SwiftUI。
- **版本证据**：预览来自已构建的原型产物，源码来自注册仓库当前文件；二者版本不一定一致。大改前必须重新构建，并记录对应源码 revision、屏幕 ID、截图时间和设计状态。

## 每次有意义的视觉 Review

在相同的 **393×852 iPhone** 条件下检查正常、空、密集、错误/恢复状态；有条件再覆盖窄屏、长中文/英文、深色、高对比及动态字体。做一次真实任务：进入→输入→保存或取消→历史/详情→更正/删除或恢复→回到入口。评估操作是否可发现、语义是否准确、文字是否裁切、主行动是否突出，保留 V1 有效的专业信息层级。若只是静态截图，明确注明不能代表 Flow Done。

参考：Apple Human Interface Guidelines 的 Layout、Designing for iOS、Design Principles；W3C WCAG 2.2（对比、焦点、触控目标）。平台指导是外部基线，肾宝保具体医疗语义仍以本仓库合同为准。
